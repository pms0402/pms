# 0.16.1 · 시작 로딩

0.16.0은 이동 중의 이미지 가공을 없애려고 원본 다운로드와 2,753칸 추출을 모두 시작 화면에서 끝냈다. 원본 82장의 전송량만 약 185.9 MiB였고, 이미지 두 장을 처리할 때마다 다음 다운로드를 시작했다. 멈춤 대응 작업이 시작 대기를 길게 만든 것이다.

이번에는 같은 픽셀을 개발 도구에서 미리 추출해 여섯 아틀라스로 묶었다. 실행 중에는 이 파일과 배경·이야기 그림 열 장을 읽는다. 그림 해상도와 애니메이션 장수는 줄이지 않는다.

| 항목 | 0.16.0 | 0.16.1 |
| --- | --- | --- |
| 시작 이미지 파일 | 82개 원본 PNG | 아틀라스 6개 + 배경·이야기 10개 |
| 이미지 전송량 | 185.9 MiB | 41.7 MiB |
| 브라우저에서 추출·팔레트·알파 가공 | 2,753칸 | 0칸 |
| 유지 래스터 픽셀 | 약 144 MiB | 약 156 MiB |

매니페스트·아이콘까지 합친 실제 초기 아트 응답은 약 42.0 MiB다. 래스터 바이트는 아틀라스 여백 때문에 조금 늘지만, 최대 2,048×2,048인 여섯 비트맵을 공유한다. 원본 전체를 디코딩해 유지하거나 수천 개 캔버스를 만들지 않는다. 이 수치는 브라우저 전체 메모리가 아니다.

무손실 WebP를 사용한다. 반투명 폐허 배경은 브라우저의 알파 계산 차이를 피하려고 PNG 원본을 그대로 복사했다. 원본 PNG, 논리 셀 크기, 발·장비 기준점과 판정은 유지한다. 소스 추출 도구는 개발용으로 남아 있고 플레이 중 호출하지 않는다.

파일명에는 내용 해시를 붙인다. 모듈 버전만 바뀐 업데이트에서는 같은 이미지를 다시 받지 않는다. 준비된 이미지는 별도 CacheStorage에 보관하고, 현재 매니페스트에 없는 이전 파일만 지운다. 이 캐시는 게임 저장 데이터와 분리되어 있다. 저장 접근 거부나 용량 제한이 있으면 HTTP로 읽어 계속 실행한다. Safari 비공개 모드처럼 저장 유지가 제한되는 환경에서는 재접속 시 다시 받을 수 있다.

## 제작과 검사

개발 서버를 실행한 뒤 `npm run art:pack`으로 준비 파일을 만든다. Node, Chromium과 FFmpeg/libwebp를 사용하며 원본을 수정하지 않는다. `npm run build`와 단위 검사는 원본·추출 코드의 입력 해시, 파일 해시, 모든 셀의 경계와 겹침을 확인한다. 오래된 준비 파일은 빌드를 통과하지 못한다.

`npm run test:loading`은 일반 브라우저 프로필에서 첫 실행과 재접속을 검사한다. 2,753칸 전체의 SHA-256과 배경·이야기 그림 열 장의 화면 픽셀을 원본과 비교하고, 재접속 때 준비 이미지 16개가 캐시에서 읽히는지 확인한다. 저장을 막은 별도 컨텍스트의 HTTP 대체 경로도 검사한다. `BROWSER_ENGINE=webkit`으로 같은 검사를 실행할 수 있다.

로컬 WebKit에서 기존 준비 완료는 약 9.8초였다. 변경 후에는 일반 프로필에서 첫 실행 약 3.3초, 재접속 약 1.5초였다. 측정과 캐시 사용량은 `test-results/017-loading-webkit.json`에 기록한다. 로컬 측정은 다운로드 환경이 빠른 개발 서버의 결과이며, 실제 iPad의 통신 속도나 처리 시간을 보장하는 수치가 아니다. 실제 iPad 기기를 원격 조작한 검사는 아니다.

기존 전투·체크포인트·보스·성장·저장 형식은 바꾸지 않는다. 단위 검사 261개, Chromium/WebKit의 이동·복구·재접속, 실제 터치 입력과 중간보스 일곱 전투를 확인했다.
